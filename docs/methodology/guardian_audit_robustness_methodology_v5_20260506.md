## Pass 17 詳細 — 動的状態確認（Dynamic State Verification）

### 名称
Pass 17 — 動的状態確認（Dynamic State Verification）

### 目的
起草対象が依存する **動的状態**（リポジトリの実 commit / テスト実行結果 / working tree 状態 / 実機動作 / ファイルシステム実物）を起草着手前に確認する。Pass 16（静的 read）はコード・仕様書・DB の「あるべき姿」を確認するが、現実の動作・状態とは乖離しうる。Pass 17 はこの「乖離」をブロックする。

### 由来
- **失態 #52**（S129 / 2026-05-05）: working tree 未確認で commit/push 指示文起案
- **失態 #53**（S130 / 2026-05-05）: 📍最新誤認 / 古い状態を前提に判断
- **失態 #57**（S132 / 2026-05-05）: B-024 既実装済を git log Pass 16 漠認で見落とし → 重複指示文起案
- **失態 #54**（S130 / 2026-05-05）: recent_chats ツール未使用（→ Pass 18 もカバー）
- 関連: アドバイザー S88/S89 B-022 推奨案訂正（コード read のみで `/tmp/kirin/` 動作を推測 → 訂正）

### 判定基準
起草者は以下を **起草着手前** に実施する:

1. **git log / commit body 確認** — 「これから実装する」内容が既に commit 済でないか確認（B-024 失態の直接対応）
2. **cargo test / npm test 実機実行結果** — baseline 数字（pass/fail/skip 件数）を実測。文書内コピーではなく実測値
3. **working tree 状態** — `git status` で未 commit 変更を把握。stash / branch も把握
4. **実機動作確認**（必要な場合）— xtask install / Studio One 実機 / npm run start 等
5. **ファイルシステム実物**（必要な場合）— `~/Library/Application Support/Kirin OS/...` 等の実パス確認
6. **記録形式** — Pass 14/15/16 と同様「Pass 17-A 適用記録」セクションを起草成果物に埋め込む

### 適用手順（Pass 17-A）
```
Step 1: 動的状態リスト起票
  | git log（直近 N commit / 起草対象に関連するもの）
  | cargo test / npm test（baseline 取得）
  | git status（working tree）
  | 実機ログ（必要な場合）

Step 2: 各状態を実取得
  | git log → bash で実行（推測ではなく実出力）
  | cargo test → 実行 + 結果記録
  | git status → 実行 + 結果記録

Step 3: 「Pass 17-A 適用記録」セクションを起草成果物に埋め込む

Step 4: 起草中に状態が変化した場合
  | 同様に再取得（記憶や推測で書かない）
```

### 適用スコープ
**全部屋 / 起草者全般**。特に以下のケースで必須:
- 実装指示文起草（重複指示防止 / 失態 #57 直接対応）
- commit/push 指示文起草（working tree 未確認防止 / 失態 #52 直接対応）
- baseline 数字を含む文書起草（実測値優先 / 失態 #53 関連）
- 既実装/未実装の判断（git log Pass 16 漠認禁止）

チャット返信・軽微修正・口頭説明は適用外。

### Pass 16 との関係
- **Pass 16（静的 read）**: 仕様書・コード・DB の「定義」を実 read で確認
- **Pass 17（動的状態）**: 「現状」を git/test/実機で確認
- **両者は補完関係**: 静的定義 ≠ 動的現状 のため両方必要

## Pass 18 詳細 — チャット履歴一次ソース（Chat History as Primary Source）

### 名称
Pass 18 — チャット履歴一次ソース（Chat History as Primary Source）

### 目的
Notion タスク一覧・他部屋起草 md・引継ぎノートは **二次資料**。Daisuke と Claude の chat history を **一次ソース** として上位に置く。Notion は遅延同期で構造化された二次情報、chat は最新の確定情報。混同してはならない。

### 由来
- **番人 #137 §2.7 karaoke 判断要請 全面撤回**（2026-05-05）: アドバイザー起草 md の「未設計」ステータスをそのまま受け入れて判断要請を起草 → Daisuke「別ファイルですでに作っている」指摘 → recent_chats 再取得で 2026-03-27 / 04-19 / 05-04 の事実を発見 → 全面撤回
- **失態 #54**（S130）: recent_chats ツール未使用
- **失態 #46**（S128）: Q推奨根拠立証謎遠さ（chat history 由来の前提が見えていなかった可能性）

### 判定基準
起草者は以下を **起草着手前** に実施する:

1. **論点別 conversation_search** — 起票直前にその論点キーワードで `conversation_search` を必ず走らせる。Notion 起草資料に「未設計」「未確定」と書かれていても、Daisuke が chat で動かしている可能性がある
2. **recent_chats 複数クエリ** — 1 回の取得（例: 15 件 desc）では不足。複数クエリ（recent_chats コア + conversation_search トピック別）で重ねる
3. **Notion を「参考資料」に格下げ** — Notion タスク一覧・アドバイザー起草資料は参考資料にとどめる。chat history を一次ソースとして上位に置く
4. **「未設計」ステータスの受入禁止** — アドバイザー起草 md の「未設計」「未確定」を額面で受け入れない。最新の chat で状態を確証してから起票
5. **「読み飛ばしなし」と言わない** — 「何件をどのクエリで取得 / どの論点をカバー」を具体的に記述。"漠認" は Pass 16 違反

### 適用手順（Pass 18-A）
```
Step 1: 起草対象の論点キーワード列挙
  | 例: 「karaoke リファレンス」「stem_quality_factor」

Step 2: recent_chats（直近 20 件 desc）+ conversation_search（論点キーワード）を実行
  | 結果が見つからない場合は別キーワードで再検索

Step 3: 取得した chat history と Notion 文書を照合
  | 矛盾発見 → chat 優先で訂正

Step 4: 「Pass 18-A 適用記録」セクションを起草成果物に埋め込む
  | 取得件数 / クエリ / 確認した論点をリスト化
```

### 適用スコープ
**全部屋 / 起草者全般**。特に以下のケースで必須:
- 判断要請起草（番人 #137 karaoke 撤回の直接対応）
- 仕様策定起草（Daisuke 直近指示の取り込み）
- 「未設計」「未確定」と Notion で書かれている事項に手を出すとき
- 部屋間 Handoff 受領後の継続作業

### 「Notion のみの判断絶対禁止」原則の体現

## Pass 19 詳細 — 引用元三軸確認（Source Citation Triple-Check）

### 名称
Pass 19 — 引用元三軸確認（Source Citation Triple-Check）

### 目的
他文書からのコピー/引用時、引用元と現状の乖離をブロックする。Pass 16 が「参照元の存在を read で確認」するのに対し、Pass 19 は「引用元の主張内容が現在も妥当か」を 3 軸で確認する。

### 由来
- **失態 #62**（S135 / 2026-05-06）: 引継ぎノート §3「Daisuke 確認待ち 2 件」を鵜呑み → 実際には Daisuke に質問していなかった → 起動報告で false claim → Daisuke「質問された記憶ない」指摘で発覚
- **失態 #63**（S135 / 2026-05-06）: Handoff #3 起草時に監査 md §0 baseline 数字（419/416/0/3）を機械コピー → S134 時点値 / 現行 436/433/0/3 と +17 件乖離 → Lens CC 自前確認で実害なし
- **失態 #64**（S135 / 2026-05-06）: 監査 md §B5「stem_quality_factor 完全不在（grep 0 件）」を鵜呑み → CC R-9 再監査で別命名 `stemQualities` で部分実装判明 → 「完全不在」誤り

これら 3 失態を統合した「鵜呑み防止」3 軸:
- #62 = **言質の出所**（人がそう言ったとされる事実）
- #63 = **文書の時点性**（数字・状態・指標）
- #64 = **文書の調査範囲**（grep / search / 検索結果）

### 判定基準

| 軸 | チェック内容 | 確認手段 |
|---|---|---|
| **(a) 言質の出所** | 「Daisuke が言った / 番人が確定した」とされる事実 | recent_chats / conversation_search で当人発言を直接確認 |
| **(b) 作成時点 vs 現状の差分** | 数字・指標・状態（baseline / pass数 / commit hash 等） | git log / cargo test / npm test 実測値を優先（Pass 17 連動） |
| **(c) 調査範囲の網羅性** | grep / search 結果の引用 | キーワード網羅性（大文字小文字 / 別命名 / 部分一致 / 代替表記）を確認。必要なら CC に R-9 再検証依頼 |

### 適用手順（Pass 19-A）
```
Step 1: 引用元文書のリスト起票
  | 例: 引継ぎノート / 監査 md / Daily Brief / 確定判断DB

Step 2: 各引用について 3 軸チェック
  | (a) 言質: chat history で直接確認
  | (b) 時点性: 実測値で更新
  | (c) 網羅性: 別キーワード / 代替表記で再検証

Step 3: 「Pass 19-A 適用記録」セクションを起草成果物に埋め込む
  | 引用 N 件 × 3 軸 = 3N チェック結果を記録

Step 4: 差分発見 → 元文書ではなく現状で起草
```

### 適用スコープ
**全部屋 / 起草者全般**。特に以下のケースで必須:
- 引継ぎノートを参照する起動報告（失態 #62 直接対応）
- 他文書からの数字コピーを伴う指示文起草（失態 #63 直接対応）
- 監査 md の grep 結果引用（失態 #64 直接対応）
- 部屋間 Handoff の中継

### Pass 16 との関係
- **Pass 16**: 参照元の **存在を確認**（実 read 完了）
- **Pass 19**: 参照元の **主張内容が現状も妥当か確認**（3 軸チェック）
- **両者は補完**: read しただけでは古い情報を引き継ぐ可能性がある

## Pass 21 詳細 — 概念区別（Concept Distinction Check）

### 名称
Pass 21 — 概念区別（Concept Distinction Check）

### 目的
類似用語・並存する概念が存在するとき、起草前に区別を明文化する。区別なしで起草すると概念混同が発生し、深刻な手戻り（最悪 Daisuke のプロジェクト中止判断）を招く。

### 由来
- **失態 #37**（S124 / 2026-05-05 / Daisuke Hypha 一旦中止の **直接原因**）: 重大概念混同 = 「複数 Keep 並存」と「1 PRE 多 POST 紐付け」の取り違え
  - PRE 1:1 排他（現仕様）
  - 複数 Keep 並存（S110 α-5 (a) / 上限 13）
  - これら別概念を混同 → 仕様調査責任放棄（失態 #35）/ 検証構成設計ミス（失態 #36）と連鎖 → Daisuke「完全にやる気を失った」
- 関連: 失態 #46（Q 推奨根拠立証謎遠さ）/ #48（Gap リスト誤定）

### 判定基準
起草対象に類似用語・並存概念が含まれる場合、以下を実施:

1. **並存概念リストアップ** — 起草対象が触れる概念のうち、似た用語・関連概念を列挙
2. **区別マトリクス作成** — 各概念について「定義 / 出典 / 適用範囲 / 他概念との違い」を 1 行ずつ書く
3. **起草成果物への明記** — 「本起草で扱う概念は X / Y は別概念で扱わない」を冒頭明記

### 適用手順（Pass 21-A）
```
Step 1: 並存概念検出
```

## 起草行動規則（v5 恒久ルール / 全部屋適用）

全部屋の起草者は新規フィールド / 機能 / 仕様書 / 指示書 / 判断要請 / 実装指示文の起草着手前に以下 8 点を必ず実行する:

### 動機側
1. **目的の言語化（Pass 14）** — 「このフィールド/機能/指示がシステムでどう使われるか」を 2-3 文で書き出す。書けないなら起草しない

### 入力側

6. **引用元三軸確認（Pass 19）** — 他文書から引用する場合 (a)言質 (b)時点性 (c)網羅性 を確認

### 出力側
7. **既存仕様書との二重定義チェック（Pass 15）** — 起草対象が既存仕様書で既定義・既決定している事項を上書き / 被り起草していないか確認
8. **推奨完備（Pass 20）** — 推奨明示・工数非材料化・一括提示禁止・R-9 確証
