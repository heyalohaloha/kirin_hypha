HTML一式は`index.html`、ローカル音源、波形データ、素材台帳で構成する。

見本の実装コードは流用せず、GPLのHypha向けに独立実装する。

- 本文は16 px以上、主要操作は44 px以上を目安にし、100〜200%表示で欠けを確認する。
- 1件ごとに保存し、次回は未回答から再開する。「判定済み」「判断不能」「再生不可」「未回答」を分けて集計する。
- 不完全な結果もJSONで出力し、別のブラウザや改訂後のパックへ読み込めるようにする。TSVは閲覧用に併設する。

境界が曖昧な場合は不確かさを残し、精度評価の分母と除外規則を先に決める。

## 5. SPACEと2MIX ATTACKを完成させる

SPACEは、広帯域EARLYと20 dB相当減衰時間の承認範囲を維持する。
奥行き、RT60、DEPTH、REPEAT、帯域別解析は今回追加しない。
既存の表示、固定区間計算、研究用自動解析を一覧化し、同じ機能名で別定義を使う状態を解消する。
接続先は一つの定義IDを共有する計算器、PRE/POST共通区間、snapshot、表示、Captureとする。

1. 人が指定した区間で計算器を試験し、計算の問題と自動選択の問題を分離する。
2. 現行1,775候補の棄却理由と人の区間を照合する。SPACEに適した連続区間を選び、ATTACK候補の過分割をそのまま引き継がない。
3. EARLYの0〜80 ms / 80〜250 ms、左右のpower平均、整数sample境界、D20の傾きと採用条件を独立参照と照合する。
4. PRE/POSTは同じ起点と採用区間を使う。同一入力と固定ゲインで期待する不変性を確認し、イベントごとの差分から集計する。
5. ノイズ床、次の音、再上昇、持続音、fade、gate、欠測を区別する。有効な区間がない場合は理由を示し、偽の数値で埋めない。

2MIX ATTACKはDRUMと別の検出定義、尺度、評価を持たせる。
研究用検出器を注釈へ合わせ、密度別、音色別、加工別の誤検出と取りこぼしを確認する。
TRACK/STEMのDRUMは既存の測定意味を維持し、文脈切替では旧profileのrequest、queue、履歴を終了する。
同時に二つのprofileを動かして負荷を増やさない。

| 評価 | 既存計画の条件 | 固定するタイミング |
| --- | --- | --- |
| 2MIX検出 | Precision ≥0.85、Recall ≥0.75、F1 ≥0.80、時刻誤差P95 ≤15 ms、FP ≤1回/秒、signed medianの絶対値 ≤48 kHzの1 hop | 対応許容幅、fold、注釈間F1 ≥0.90、曖昧な境界の扱いとともに、未使用評価を開く前 |
| SPACE計算器 | EARLYの独立参照差 ≤0.01 dB、既知直線の傾き相対誤差 ≤1e-6という初期案 | 計算器の独立試験前。実音の精度保証と混同しない |
| SPACE自動区間 | 適格区間の採用Precision ≥0.95、Coverage ≥0.70という提案 | 区間の対応規則、必要な標本数、曲別集計、PRE/POST共通区間の最低Coverageを開発評価後に確定 |

SPACEの共通区間Coverageなど、既存計画で未確定の値は確定済みと書かない。
開発結果から推奨値と利用できる頻度をまとめ、意味や適用範囲が変わる箇所のみ承認を受けてから評価器と候補を固定する。
候補hash、係数、定義ID、素材と評価器の版を固定した後、未使用履歴を確認した別曲で評価する。
ATTACKの評価予約曲をSPACE開発で開くことも避ける。
最終評価を見て調整した場合は開発用へ移し、新しい未使用素材で再評価する。

不合格時は失敗した条件と改善量を記録し、同じ調整を繰り返さず選択方法を見直す。
採用率を上げるためだけの閾値緩和、手動専用への変更、対象音源の限定は自動的に決めない。
計算定義に依存しない容量制限、世代管理、排他、無効状態の表示は先行して整備できるが、未合格の検出器を利用者向けに有効化しない。

## 6. 軽量化と既存指摘を閉じる

CPUはAudio Thread、計測worker、通信、描画を分け、同じ最適化条件と入力で比較する。
部品の削減率をHypha全体の削減率として報告しない。
macOSのDRUM性能不合格は、測定中の外部負荷も記録して再現を調べる。
他プロセスのせいと断定せず、合格した回だけを採用しない。

| 領域 | 残す表現と機能 | 合格条件 |
| --- | --- | --- |
| DRUM | 上部は形、大きさ、左が過去で右が現在の時間軸。下部は質、四量、繊細なグラデーションと膜の変化 | 既存予算の更新中央値1枠12 ms / 2枠16 ms、最大24 ms、初回80 msを緩めない。製品フォントと実ホストでも測る |
| Spectrum / Focus Trail | 履歴の流れ、連続した比較表示、POST単体の面積 | 更新中の4.5 ms予算超過を閉じる。描画、hover、clickが同じ幾何を使う |
| 計測と通信 | 正本の窓、精度、heartbeat、pair喪失検出、Record | 通常出力bit identical、0 latency。停止中、複数配置、待機枠で不要な解析と再描画が残らない |
| 新規解析とBlind | 必要な場合だけ動くworkerと事前確保された比較コピー | 最大bytes、準備時間、queue使用量、drop、callback最大/P99、worker CPUを記録し、固定した予算内に収める |

負荷試験には1解析枠、2解析枠、3番目の待機、複数の非表示インスタンスを含める。
192 kHzを含む対応sample rate、可変block、10分以上の連続再生、停止と復帰を確認する。
利用者向けの最大構成を固定してから新規workerのCPUとメモリ上限を決め、測定後に上限を引き上げて合格にはしない。
既存のAudio Thread単体CPU目標0.1%未満は、測定方法とCPU換算の分母を明記して検証する。

| ATTACK、DRUM | 不要なFOCUS等のhit target、左右ラベル、上部の細線、音と表示の同期、停止と無音の黒表示、明示LOCKだけの保持、下部四量とFRONTの読み取り |

文字の修正は共通Typographyとレイアウトから行い、一つの画面だけを拡大して終えない。
装飾を追加して測定意味を曖昧にせず、DRUMの動きを人工的な発振や重い物理計算で補わない。

## 7. 構造と影響ファイルを先に揃える

製品変更前に、以下の既存責務と対応テストを一度に照合する。
既にある部品へ接続し、同じ目的のSPACEやBlind実装を別の場所へ新設しない。

| 責務 | 主な確認箇所 |
| --- | --- |
| Blind | `juce_shell/src/local_blind/`、`PluginProcessorAudition.cpp`、processor/editorの開始操作、ホストclockとscope |
| 共通排他 | `analysis_lease`、既存Reference runtime、Keep / All Keep、Record lifecycle |
| SPACEとATTACK | `kirin_measure`のprobeと計算器、`attack_runtime*`、`attack_detail`、PRE/POST exchange |
| ABIと表示 | `kirin_hypha_ffi`、`PluginProcessorAnalysis`、`PluginEditorAnalysis`、`HyphaSpacePainter*`、`HyphaAttack*`、Observationのpage契約 |
| 共通UIと負荷 | `HyphaTypography*`、`HyphaTheme*`、`HyphaSpectrum*`、Observatory、snapshot比較 |
| テストと仕様 | Rust、FFI、native UI、VST3実出力、product contract、invariants、出荷ソース検査 |

現在はReferenceとSpectrumなどに既存の未コミット作業がある。
その内容と所有範囲を保存し、Blindの共通排他へ関わる変更だけを照合して統合する。
他作業の途中状態を完成コミットに混ぜず、同時変更が衝突する場合は対象ファイルへの書込みだけを保留する。
新規owned sourceは500行以下とし、変更対象の巨大ファイルは該当責務を先に抽出する。
既存の行数超過も最終の出荷検査では隠さない。

## 8. Windows検証と最終合格

Windows検証機の利用許可は受けている。
操作前に[共通Runbook](/Users/nishiodaisuke/Dev/kirin_sense_lens/docs/windows_validation_remote_access.md)を読み、認証情報を出力せず、既存の許可されたGUI経路を確認する。
直近の作業ではSSHによる部品試験までで、DAWを操作する経路は使えていなかった。
GUI経路が利用できない場合はその実機工程だけを保留し、セキュリティ設定や常設サービスを勝手に変更しない。

検証曲は次の保存済みプロジェクトに固定する。
元の`.dawproject`を開くショートカットを使って別番号の曲を作らない。

```text
C:\Users\hello\OneDrive\ドキュメント\Studio Pro\Songs\Peach_Hypha_Demo(13)\Peach_Hypha_Demo.song
```

まず既存のStereo条件を確認し、monoは別の明示した試験条件として追加する。
PRE/POST両方の読み込まれたbuild IDとbinary hashを記録し、古い配置を見て修正の合否を決めない。
macOSとWindowsで同じ候補の機能と停止動作を確認する。
検証用ビルドと一時配置は実装途中に必要であり、すべて終わるまでビルドしないという順序にはしない。

最終合格は次の証拠が揃った状態とする。

- Rust workspace testとClippy、本体警告ゼロ、C++試験、出荷ソース検査。FFI変更時はignored parityとpairing_candidatesも実測件数で全件合格。
- PRE/POSTの通常出力、offline、bypass、sample rate変更、worker障害と再起動、欠損ファイル、旧版混在の試験。
- Blindの操作一巡、PDC、Record排他、枠の競合、短音、mono、減衰保持と通常復帰。公開対象形式での実ホスト結果。
- SPACEと2MIX ATTACKの独立評価、PRE/POST対応、欠測、長時間と容量上限の結果。
- 全画面の可読性、PSB、DRUM、Focus Trail、無音と停止、性能予算。音と表示の遅れは実測し、画面録画だけでゼロ遅延とは言わない。
- DaisukeがHTMLと音付き動画で回答した知覚上の問題を修正し、該当条件を再試験した記録。

HTMLへ載せる動画は実際の候補を録画し、音声と映像の時刻差を確認する。
合成描画画像は合成と明記する。
既知の指摘は「修正」「再現せず」「適用外」を根拠付きで閉じ、実行できなかった試験は未検証のまま残す。
「レビュー指摘0件」は既知の未解決指摘をなくす目標とし、将来の不具合ゼロを保証する表現にはしない。

## 9. 配布準備との区切り

機能実装の完了、実機検証の完了、配布物の準備完了を別々に報告する。
公開準備へ進んだ場合は、[LSリリースRunbook](ls_release/kirin_hypha_ls_runbook.md)に従う。

1. LS用の署名済み、notarize済みmacOS Universal `.pkg`と検証情報。
2. HP無料配布用の署名済み、notarize済みmacOS Universal `.zip`、GitHub Release、英日HPリンク。
3. 同じコミットのgreenなWindows CI artifactから作る署名済みInno Setup `.exe`。PRE/POST payload、installer、uninstallerの署名とinstall、同版再install、旧公開版からのupgrade、uninstallの合格。

Windowsの手動VST3 zipを公開installerの代用にしない。
証明書、署名、CI、installer実動検証の不足があれば、公開全体のblockerとして記録する。
今回の計画作成は署名、notarize、公開、pushを実行する承認ではない。
